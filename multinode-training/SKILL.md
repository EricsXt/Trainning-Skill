# 多机训练：先验证，再占用排队资源

目标是减少可提前发现的错误，保护现有任务和排队位置。遵守用户选择的框架、数据、集群和提交顺序。此 skill 本身不授权停止任务、申请额外 GPU 或上传文件；在用户已授权的范围内直接完成必要检查，不重复索要许可。

## 先建立当前事实

读取项目 AGENTS.md、实际入口脚本、环境配置、训练代码、平台运行时定义和现有任务状态。确认真实执行链：平台 → 每节点入口 → 框架控制进程 → GPU。不要仅依据旧脚本名称或平台的 torch/JAX 标签判断。

保存一份不含凭据的任务记录：节点数、每节点 GPU、CPU/内存、镜像、挂载、源码版本或哈希、数据版本、初始化方式、batch 契约、优化器、保存计划、W&B run 和输出路径。每个尝试使用独立输出和 run 名；保留旧配置、根因及测试证据，不修改不可变的数据契约。

按成本递增执行以下验证。把每项标为 **已验证 / 不适用 / 等待实际分配验证**，附证据和范围。没有实际多机实验时，不能称“多机检查全部通过”。

## 1. 提交前：无需 GPU 或可在现有资源验证

- **环境闭包**：镜像负责 OS/CUDA 等系统依赖；持久磁盘上的 Python 环境不保证系统库齐全。确认 Python、解释器软链接目标、tokenizer、NCCL、IB provider 及其依赖在所有节点均可见。凭据使用私有文件/平台 secret，不读出到终端或写入仓库。不要 source 整份 shell 启动文件提取密钥。
- **路径与数据**：检查挂载路径及只读/读写属性、共享输出可写性、源码和 SDK 版本、数据索引、归一化统计。以真实 dataloader 读取少量图像、动作和文本，验证 shape、dtype、有限值和时间对齐。样本数可能是帧锚点而非轨迹数，必须说明计数单位。警告按实际使用的字段判断，不能一概忽略。
- **入口**：做 shell/Python 语法检查，实际展开环境变量并核对参数；只打印白名单配置。确认平台究竟执行一次/节点还是一次/GPU，避免嵌套 torchrun。协调地址取当前分配提供的值；端口、rank、world size 按框架语义配置，不统一套用。
- **batch 契约**：纯数据并行时，global batch = 每个数据并行副本的 microbatch × 数据并行副本数 × 梯度累积。混合并行须明确 DP 数，不能乘全部 GPU。区分节点 batch、每 GPU batch、microbatch、global batch，以及 microstep/optimizer step。修改卡数不会自动意味着修改 global batch。
- **初始化**：显式选择 base / weights-only / full-state resume。full resume 检查模型、优化器、EMA、step、随机状态和数据游标，验证 batch、数据、归一化、学习率计划的兼容性。batch 改变时不得直接将旧 step 当成新 batch 的游标；选择并记录明确的迁移方式或从 base 重启。不要擅自改变用户指定的恢复点。
- **训练量与保存**：从真实采样器计算 epoch；记录 drop_last、尾样本和重采样语义。batch 改变后重新计算总更新次数、warmup/decay 和每 epoch 保存里程碑。保持峰值学习率还是调整，必须有显式决定；不能机械线性放大学习率。
- **共享目录回归（关键）**：在同一共享目录上启动至少两个实际框架进程，执行与生产相同的 checkpoint 初始化路径，覆盖全新目录、空目录、有效断点。不要让各 rank 根据瞬时 `exists()` 分别选择 resume/overwrite。创建与恢复决策应跨 rank 一致；绝不以覆盖已有权重解决竞态。先前仅 resume 成功，不能证明从 base 启动正确。

可用 `scripts/check_plan.py` 校验纯数据并行的 batch/epoch 计划。格式见 [references/plan-example.json](references/plan-example.json)。该脚本不能证明 dataloader、网络或 checkpoint 正确。

```bash
python3 scripts/check_plan.py references/plan-example.json
```

## 2. 获得分配后：在实际容器做物理验收

优先利用现有已授权分配，不因仅修改挂载脚本而取消排队任务。若入口支持，在同一任务内先短测再继续正式训练，避免单独排队购买一次 smoke run。不能在不同 NCCL 初始化状态下静默降级或让一个 rank 单独继续训练。

- **DNS 和 TCP**：记录实际协调 hostname，等待平台服务 DNS 就绪；仅对临时解析错误做有上限的重试，保留首个错误。验证双方解析结果和实际 rendezvous 连通性。重试耗尽需要调查地址/服务，不自动再次提交。UDP route 选择只能证明本地选路，不能证明对端端口可连。
- **网卡和 IB**：读取当前容器网卡、地址、UP 状态和到主节点的路由。文档中的 bond0/mlx5 名称只是该环境的示例，不能硬编码到新分配；显式覆盖无效应报错。检查实际暴露的 `/dev/infiniband`、libibverbs、provider、active port 及设备能否打开；只看宿主机 sysfs 清单不够。保持用户的 IB 要求，不能静默改为 socket。
- **全体设备与通信**：检查每个节点可见的卡数、进程绑定、框架 local/global device 数，执行真实跨节点 collective。设备打开成功不等于 collective 成功，collective 成功也不等于训练成功。
- **真实训练路径**：使用实际模型、目标精度、目标 batch、数据转换及并行模式完成参数更新。观察有限的 loss、梯度范数、学习率，并确认所有 rank 同步推进。检查梯度累积边界以及每次 optimizer update 的实际样本数。
- **保存与恢复**：使用生产 checkpoint 路径和代码，完成一次保存、读取完整性检查、恢复和后续更新；不要只验证模型权重文件存在。若需要短测保存，使用独立 smoke 输出，不把短测权重标成正式 epoch。既有证据可在对应代码/环境/模式未变时复用，但必须注明它未覆盖的新模式。

只读环境检查：在每节点运行 `scripts/node_preflight.py`。它报告 GPU、网卡、DNS/选路和可选的 IB 设备打开情况，**不初始化 NCCL，不执行训练，也不证明带宽或远端 TCP 连通**。实际环境信息可能敏感，报告留在私有工作区。

```bash
python3 scripts/node_preflight.py --expect-gpus 8 --coordinator-host "$MASTER_ADDR" --coordinator-port 29520 --require-ib
```

## 3. 提交、替换与退出策略

核对用户指定的镜像、资源池、节点/卡数、优先级、挂载、secret 路径、命令和输出目录。优先级用平台实际接受并读回的值，不猜字段，不宣称 high 保证立即调度。

若用户要求“先提交替代任务，再停止旧任务”：先完成替代配置与测试 → 提交 → 读回 job ID、参数和有效状态 → 才停止指定旧任务 → 确认已停止。创建失败则保留旧任务；不要顺手停止本地训练或其他任务。

排队时保留原 job，检查调度原因：GPU、CPU、内存、资源池配额或整组调度；修改已提交的资源/镜像/命令不一定生效。不要为催排队盲目取消重提。共享脚本在启动时读取的改动需记录哈希；运行中的 Python 不会自动加载磁盘修复。

一个错误必须先定位首个异常、修复并完成针对性回归，才能在既有授权范围内重提一次。相同错误复发时停止自动重提，保留证据并解释阻碍。用户要求保持队列位置时，不取消任务；若故障确需替换，应说明理由并遵循当前授权。具体失败模式见 [references/failure-patterns.md](references/failure-patterns.md)。

## 4. 启动后的验收和持续观察

按下列状态报告，禁止把平台 Running 当成训练成功：

`已提交/排队 → 容器启动 → 通信通过 → 数据/模型加载 → 首次编译 → 实际更新 → 已保存 → 恢复验证`

用带时间戳的两个节点日志、框架状态和 W&B history 交叉验证。启动耗时不是稳定 step 耗时；恢复起点也不是本次新完成步数。没有 loss 时先确认训练端是否产生标量，再检查日志 flush、解析、上传和图表 namespace，避免对正常训练反复重启。

最低记录：loss、optimizer step、数据 epoch/样本暴露、LR、梯度范数、实际 global batch、精度、step 耗时、samples/s、数据等待、checkpoint 路径/完成次数、各节点 GPU 负载/显存，以及可复现配置。没有验证集就标记“无验证指标”，不要编造 validation loss。

统计吞吐时排除首编译，比较多个连续窗口，分别给出典型耗时、包含停顿的实际平均值、样本数和区间。checkpoint I/O、数据尾延迟及多卡通信可能导致波动。GPU 100% 表示持续有 kernel 执行，不证明算力饱和；显存空余也不自动说明应该增大 batch。

后台监控应增量读取日志或读取有界尾部，使用锁防止重复启动，记录健康状态与时间戳，不反复全文读取数 GB 的 NCCL 日志。限制 verbose 日志/按需轮转；不要在尚需诊断时清空错误证据。后台只读监控不等于助手会自动推送消息，需明确实际通知能力。

## 交付

给出当前 job/run 链接、实际 batch 和保存计划、已验证证据、尚待物理验证的项目、首个根因及其回归结果。未经请求不公开任务记录或凭据。只报告确实执行过的测试；skill 降低失败概率，不能保证平台、硬件和存储永不故障。
